# Road Map

I think this is exactly the right time to "coil back," as you put it. One thing I've appreciated throughout this project is that we've allowed ourselves to extrapolate the long-term vision, but we've also consistently returned to the immediate engineering objective. That discipline is what will make the vision achievable.

Looking only at the POC, I think we should ask one simple question:

> **What is the minimum additional capability that turns an observation into reusable engineering knowledge?**

The answer is **not AI**.

It is **structured interpretation**.

## Where we are today

We have successfully demonstrated:

```text
Engineering Command

↓

NodeCommandExecutor

↓

ICommandObservation
```

For the first time, CorpDesk is producing structured evidence rather than terminal text.

That is a major milestone.

## The next milestone

The next milestone should be:

```text
ICommandObservation

↓

ShellBuildAnalyzer

↓

IBuildAnalysis
```

This is the first cognitive layer.

Its responsibility is **not to solve the problem**.

Its responsibility is to **understand the problem**.

That distinction is important.

## What should the analyzer produce?

Today we have this in `stderr`:

```text
src/CdNode/sys/base/data-source.ts
```

```text
"resolve" is not exported by "__vite-browser-external:path"
```

```text
Build failed
```

Those are text.

The analyzer should transform them into something like:

```ts
IBuildAnalysis {

    stage: BuildStage.Bundle,

    sourceFile:
        "src/CdNode/sys/base/data-source.ts",

    module:
        "path",

    symbol:
        "resolve",

    classification:
        BuildClassification.NodeModuleInBrowser,

    severity:
        Error,

    confidence:
        1.0
}
```

Notice there is still no solution.

Only understanding.

## This is where the knowledge loop begins

Once the analysis is structured, the next participant becomes almost trivial:

```text
IBuildAnalysis

↓

KnowledgeProvider

↓

Known?
```

If known:

```text
IBuildDecision
```

If unknown:

```text
AI

↓

Candidate Solution

↓

Validation

↓

KnowledgePublisher
```

Notice that AI has moved much later in the pipeline.

That is exactly the supervised architecture you've been pursuing.

## I think we should postpone knowledge persistence

This may sound surprising because we've spent time discussing `KnowledgePublisher`.

I actually think we should postpone implementing it.

Why?

Because we don't yet know what the analyzer will produce.

If we implement persistence first, we'll probably change the schema several times.

Instead:

```text
Observation

↓

Analysis

↓

Decision

↓

Execute

↓

Validate
```

Only when we're happy with the shape of `IBuildAnalysis` should we persist it.

Otherwise we'll be persisting the wrong abstraction.

## My proposed roadmap

I would simplify the roadmap into six concrete milestones.

### Milestone 1 — Complete (✓)

Remote command execution.

Deliverable:

```text
ICommandObservation
```

Already achieved.

---

### Milestone 2 — Next

Implement `ShellBuildAnalyzer`.

Deliverable:

```text
IBuildAnalysis
```

Initially using deterministic parsing only.

No AI.

No knowledge.

---

### Milestone 3

Implement a small rule engine.

Example:

```text
Classification

↓

Known Rule

↓

Decision
```

For example:

```
Node builtin in browser

↓

Use browser-compatible alternative
```

Hard-coded rules are acceptable at this stage because they're helping you discover what belongs in the knowledge model.

---

### Milestone 4

Implement `ShellBuildExecutor`.

Its responsibility is simply to apply the chosen strategy and rerun the build.

This closes the engineering loop.

---

### Milestone 5

Persist validated knowledge.

Only after the analysis and decisions have stabilized.

This is when `KnowledgeProvider` and `KnowledgePublisher` become valuable.

---

### Milestone 6

Introduce AI.

Only when:

* no rule matches,
* no project knowledge exists,
* the supervisor allows it.

That keeps AI exactly where you've always wanted it.

## The very next class

If I had to choose the next class to write tomorrow morning, it would be:

```text
ShellBuildAnalyzer
```

Not because it is glamorous, but because it is the first component that transforms raw evidence into engineering understanding.

## One last recommendation

I'd make one small adjustment to the roadmap we've discussed before.

Rather than thinking of the analyzer as a parser of build logs, think of it as a **producer of engineering facts**.

For example, from your current build output, it should produce facts such as:

* The build reached the bundling stage.
* The failure occurred during Rollup/Vite bundling.
* The affected source file is `src/CdNode/sys/base/data-source.ts`.
* The imported module is `path`.
* The imported symbol is `resolve`.
* The failure indicates a Node-specific module being used in a browser build.

Those facts become the currency of the rest of the iterator. The `DecisionMaker` reasons over facts, the `KnowledgeProvider` indexes facts, AI receives facts as context, and the `KnowledgePublisher` persists validated facts and their successful resolutions. Once you make that shift, the rest of the POC naturally becomes an exercise in accumulating and reusing engineering knowledge rather than repeatedly parsing text.
